## How to extract reviewable changes

This index maps observed failures and development history to logical review units. It does not turn each prototype failure into a released-product regression. Reports specify whether evidence is a real build diagnostic, a source audit or an acceptance task. A fix present in the feature branch is not yet an upstream fix, and source coverage is not proof of a successful CI stage.

Commit links identify relevant development records. They are not a cherry-pick sequence: some early commits contain superseded designs or overlap multiple concerns. Extract the final behavior from the current head, include its meaningful regressions, and keep regenerated T4 C# with the corresponding template. Combine related issues into one PR when a single coherent change requires them.

Suggested order:

1. Extract independent bootstrap/build hardening (#4–#7) and common incremental fixes (#8–#9).
2. Establish module mode and the agreed public contract (#10–#11), including necessary interface correctness (#19), before its dependent module fixes.
3. Group Pass1 outputs (#12–#14), unresolved types and dependency collection (#15–#18), and ownership/build integration (#20–#25) by the source boundary being reviewed. Follow each report's dependencies; numeric issue order is not a buildable commit order.
4. Carry fixture/CI coverage (#26–#29) with the owning changes. Accept the full chain before claiming the native static-library graph is validated.
5. Track the independently owned C++/WinRT provider-wrapper failure (#30) separately; the fixture must remain genuinely PCH-free.

## Current external blocker

[#30](https://github.com/hoshiizumiya/microsoft-ui-xaml/issues/30) records a C++/WinRT MSBuild defect, intended for `microsoft/cppwinrt`: `CppWinRTAddXamlMetaDataProviderCpp` includes a PCH filename taken from item metadata even when the items use `PrecompiledHeader=NotUsing`. The emitted wrapper is `XamlMetaDataProvider.cpp`, which includes the component-generated `XamlMetaDataProvider.g.cpp`. It is not the XamlC T4 emitter.

[Run 36665332238](https://github.com/hoshiizumiya/microsoft-ui-xaml/actions/runs/36665332238) at the feature head passed all six product jobs. Its [module job 109742675435](https://github.com/hoshiizumiya/microsoft-ui-xaml/actions/runs/36665332238/job/109742675435) passed `CreateWinMD`, ran XamlC Pass2, then failed in `CompileXamlGeneratedFiles` with C1083 on missing `pch.h`. The log and embedded binlog source establish that specific emitter; #30 pins both package 3.0.260818.1 and the corresponding upstream target.

The module fixtures and sample now pin `YexuanXiao.CppWinRTPlus 3.1.260928.1`, whose provider-wrapper target checks `PrecompiledHeader != NotUsing`. The focused restore/import paths are updated with the package manifests. The independently maintained docs have been synchronized back to the feature branch. This is a validation dependency change, not a correction to the Microsoft package itself. Final SimpleModules link, incremental transitions, static-provider suppression, cross-project consumption and focused unit tests still need successful execution.
